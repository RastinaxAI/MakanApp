# پرامپت اجرای ممیزی خطاهای API و سناریوهای زمانی ماکان

نسخه: ۱.۰ | تاریخ: ۲۳ نوامبر ۲۰۲۶ / ۲ آذر ۱۴۰۵
این فایل دستور اجرای تست در پروژهٔ فعلی است؛ نتایج تست یا تأیید سلامت سرور نیست. ۱۰۷ سناریوی پایهٔ زیر هنوز اجرا نشده‌اند.

---

تو مسئول QA، تحلیل قرارداد API و بررسی هم‌زمانی درخواست‌های ماکان هستی. روی پروژهٔ موجود، تست اجرایی واقعی و قابل‌بازتولید انجام بده. مسئله فقط 409 نیست: همهٔ خطاهای HTTP در خانواده‌های 4xx و 5xx، کدهای تجاری، شکست‌های شبکه، پاسخ‌های ناقص و شکست‌های پنهان‌شده پشت 2xx را بررسی کن. تمرکز ویژه روی دستیار، ورود سریع/کند، آپلود زود/دیر، آماده‌سازی منبع و انتخاب/ارسال اکشن است. هدف، گزارش مستند برای تیم بک‌اند و تفکیک اصلاح فرانت‌اند، سرویس AI و زیرساخت است.

## ۱. دامنه و شیوهٔ کار

- کار را در مخزن فعلی انجام بده؛ AGENTS.md و دستورهای معتبر پروژه را بخوان. تغییرهای موجود کاربر را بازنویسی نکن.
- در این فاز منطق محصول را اصلاح نکن تا بازتولید مشکل از بین نرود. افزودن تست، fixture، ثبت رخداد کنترل‌شده و اسکریپت تشخیص مجاز است. پیشنهاد اصلاح را جدا بنویس.
- از محیط تست/محلی و حساب‌ها و فایل‌های آزمایشی موجود استفاده کن. عملیات تغییر/حذف فقط روی fixtureهای همین اجرا باشد. روی سرویس مشترک عمداً DB، storage، gateway یا provider را قطع نکن.
- نشانی Swagger قبلی: http://94.184.32.84:8090/swagger/index.html
- نشانی خروجی وب قبلی: https://testapp.makanapp.org/
- این آدرس‌ها نقطهٔ شروع‌اند؛ API_BASE_URL، WEB_BASE_URL، پروکسی، نسخهٔ build و محیط واقعی پروژه را کشف و ثبت کن. بدون بررسی، محیطی را production یا staging ننام.
- Swagger و OpenAPI زنده را بخوان؛ URL، زمان دریافت و hash آن را ذخیره کن. قرارداد زنده، کد کلاینت و درخواست واقعی شبکه را با هم تطبیق بده. اگر دسترسی نداری، بخش مربوط BLOCKED باشد؛ نتیجهٔ موفق نساز.
- کدهایی که Swagger نام برده، مدرک وقوع خطا یا پیاده‌سازی صحیح آن نیستند. مثال پاسخ یا تست mock نیز پاسخ واقعی سرور نیست.
- مسیرهای درگیرِ احراز هویت، ایجاد/بازیابی گفتگو، history، آپلود، پردازش منابع، preflight، تولید پاسخ، اکشن‌ها، سهمیه، وضعیت عملیات و ارسال فایل پیام‌رسان را پوشش بده. endpoint واقعاً موجودِ کشف‌شده را هم به پوشش اضافه کن. لندینگ خارج دامنه است.
- همهٔ اکشن‌ها، پرامپت‌های آماده و عملیات مخصوص نقش‌های واقعاً موجود را inventory کن؛ فقط یک کارت یا یک prompt نمونه را تست نکن.
- اگر کاربر علت یا لاگ قبلی ارائه کرده، آن را فرضیهٔ قابل‌آزمایش ثبت کن؛ بدون مقایسهٔ کنترل‌شده تأییدش نکن.

### سرنخ‌های قدیمی؛ نیازمند تأیید زنده

در اسناد محلی قدیمی مسیرهای زیر دیده شده‌اند، اما در این فایل اجرای آن‌ها یا وضعیت فعلی‌شان تأیید نشده است:

- POST /api/v1/ai/sources/preflight
- POST /api/v1/ai/chat
- POST /api/v1/commerce/ai/simple-text/preflight
- POST /api/v1/ai/knowledge/retrieve
- POST /api/v1/ai/knowledge/rag/answer

فیلدهای احتمالی operationId، clientOperationId، conversationId و selectedSourceIds و header احتمالی X-AI-Operation-Id را در قرارداد فعلی بررسی کن. اگر نام/نوع/معنا متفاوت بود، همان قرارداد فعلی را به‌کار ببر.
شناسهٔ اجرایی operationId را با operationId توصیفیِ عملیات در سند OpenAPI اشتباه نگیر.
کدهای AI_OPERATION_IN_PROGRESS، AI_OPERATION_ALREADY_COMPLETED، AI_OPERATION_OUTCOME_UNKNOWN و AI_OPERATION_PREVIOUSLY_FAILED صرفاً سرنخ جستجو در اسناد قدیمی‌اند، نه پاسخ قطعی سرور امروز.
preflight منابع و preflight سهمیه ممکن است قرارداد و خروجی متفاوت داشته باشند؛ آن‌ها را یک چیز فرض نکن.

## ۲. تعریف نتیجه؛ HTTP به‌تنهایی کافی نیست

برای هر اجرا، سه نتیجهٔ جدا ثبت کن:

1. **نتیجهٔ انتقال/HTTP:** پاسخ دریافت شد یا نه؟ status واقعی چیست؟
2. **نتیجهٔ تجاری/عملیات:** errorCode یا businessCode چیست؟ عملیات accepted، in progress، completed، failed یا unknown است؟
3. **نتیجهٔ تجربه و محتوا:** آیا کاربر پیام درست می‌بیند، امکان بازیابی دارد، پیش‌نویس حفظ می‌شود و پاسخ AI قابل‌استفاده است؟

قواعد:

- پاسخ 400/401/403/404/409/422 موردانتظار در تست منفی می‌تواند PASS باشد؛ آن را خودکار باگ بک‌اند ننام.
- پاسخ 200 با success=false، error envelope، HTML صفحهٔ ورود یا خروجی خراب می‌تواند شکست واقعی باشد.
- 202 یعنی پذیرش؛ اگر قرارداد job دارد تا نتیجهٔ نهایی ادامه بده.
- در SSE/stream/WS، HTTP اولیه، خطای داخل جریان و وضعیت نهایی عملیات جدا ثبت شوند؛ error frame را HTTP 500 یا 409 جا نزن.
- خطای DNS/TLS/CORS، Mixed Content، آفلاین، abort و timeout کلاینت در نبود پاسخ قابل‌مشاهده، HTTP status=null دارند. کد 0 مرورگر را پاسخ HTTP سرور معرفی نکن.
- 409 فقط «تعارض وضعیت» را مشخص می‌کند؛ منشأ دقیق باید از payload، وضعیت منبع/عملیات، request ID و لاگ معتبر روشن شود.
- status=unknown و rootCause=unknown نتیجهٔ معتبرند؛ علت حدسی را قطعی ننویس.
- در صورت پنهان‌بودن پاسخ به‌خاطر CORS، فقط آنچه دیده‌ای ثبت کن؛ وضعیت واقعی ممکن است در لاگ سرور مشخص شود.
- پیشنهاد تغییر کد وضعیت، پیشنهاد طراحی قرارداد است؛ آن را وضعیت موجود یا علت اثبات‌شده معرفی نکن.

## ۳. چهار نوع شاهد را جدا نگه دار

برای هر رکورد evidenceKind دقیقاً مشخص باشد:

- REAL_UI_BACKEND: تعامل واقعی مرورگر با سرویس واقعی.
- REAL_API: درخواست واقعی مستقیم به سرویس با fixture مجاز.
- LOCAL_INTEGRATION_FAULT: شکست کنترل‌شدهٔ dependency در محیط محلی/ایزوله.
- UI_MOCK_FAULT: پاسخ/قطع اتصال شبیه‌سازی‌شده برای بررسی رفتار کلاینت.

موفقیت دو نوع آخر، سلامت یا خرابی بک‌اند واقعی را اثبات نمی‌کند.
اگر فقط mock داری، تست واقعی متناظر NOT_RUN/BLOCKED بماند. اگر خطای تزریقی در harness فقط در فرانت‌اند است، آن را خطای واقعی provider یا gateway ننام.
شکست response پس از دریافت headers ممکن است با نرسیدن درخواست به سرور فرق داشته باشد؛ مرحله را دقیق ثبت کن.

## ۴. کشف وضعیت‌ها و لاگ‌گیری قبل از تست

ابتدا مسیر واقعی را روی یک اجرای سالم ترسیم و سپس شکست‌ها را روی آن مقایسه کن:

ورود صفحه → آماده‌شدن نشست → بازیابی/ایجاد گفتگو → انتخاب/آپلود فایل → ذخیرهٔ فایل → پردازش/نمایه‌سازی → انتخاب منابع → انتخاب کارت/ویرایش متن → preflight احتمالی → Send → پذیرش عملیات → پاسخ/stream → ثبت history و مصرف احتمالی سهمیه.

این مدل مفهومی است؛ نام stateها و ترتیب قطعی را از پروژه و قرارداد واقعی بگیر. اگر منبع API وضعیت ندارد، «آماده‌بودن تأییدنشده» بنویس؛ از رنگ آیکون نتیجهٔ backend استخراج نکن.

ثبت رخداد باید **پیش از اولین کلیک سناریو** شروع شود و همهٔ درخواست‌های وابسته را ببیند، شامل upload، poll، refresh token، preflight و retry داخلی. فقط درخواست اصلی AI را ثبت نکن.

برای هر درخواست/پاسخ ثبت کن:

- runId، caseId، variantId، repetition، attempt، requestSequence و interactionId.
- تاریخ UTC، offset نمایشی Asia/Tehran و زمان نسبی monotonic از ابتدای سناریو.
- محیط، commit/build، مرورگر و viewport، نقش fixture و زمینهٔ حساب/آموزشگاه.
- نام اکشن، متن یا hash پرامپت آزمایشی و پارامترهای مؤثر.
- روش، URL و redirect chain؛ endpoint واقعی و request ID محلی/سروری.
- headerهای غیرمحرمانهٔ مؤثر، Content-Type، Content-Length در صورت دسترسی.
- payload پاک‌سازی‌شده؛ برای فایل: نام fixture، نوع، اندازه و hash، نه محتوای خصوصی.
- conversationId، sourceId، sourceVersion، attachmentId، jobId، operationId و idempotency key در صورت وجود؛ نبودن هر فیلد را null و منشأ آن را روشن کن.
- وضعیت UI و آخرین وضعیت قابل‌مشاهدهٔ سرور برای منبع و عملیات در لحظهٔ ارسال.
- HTTP status و headerهای مرتبط، businessCode/errorCode، ProblemDetails یا envelope واقعی.
- زمان شروع، زمان تا headers، مدت پاسخ و مدت تا terminal state، در صورت قابل‌مشاهده بودن.
- response body کاملِ پاک‌سازی‌شده یا مسیر artifact آن؛ برای بدنهٔ بزرگ hash و فایل شاهد، نه حذف بی‌سروصدا.
- console error، رخداد stream/WS، close code، نتیجهٔ نهایی و اثر مشاهده‌شده روی history.
- رفتار retry خودکار، منبع retry، backoff، تعداد تلاش و تغییر/ثبات شناسه‌ها.
- نتیجهٔ expected/actual، verdict و شواهد ارجاع‌پذیر.

Authorization، cookie، refresh token، session secret، لینک امضاشده و دادهٔ شخصی/آموزشی واقعی در گزارش نماند. یک نگاشت نام مستعار ثابت برای fixtureها و شناسه‌های حساس بساز تا ارتباط رخدادها حفظ شود. trace ID عملیاتی را اگر مجاز است نگه دار.
زمان سرور و monotonic کلاینت را مستقیماً از هم کم نکن؛ اختلاف ساعت و نبود همبستگی را ثبت کن.

## ۵. روش اجرای زمان‌بندی

- یک‌بار مسیر سالم را اجرا و درخواست‌ها و state transitionها را شناسایی کن.
- تشخیص اولیه بدون retry اضافهٔ ابزار تست باشد؛ retry داخلی برنامه را تغییر نده، ولی ثبت کن. فاز بازیابی را جدا اجرا کن.
- سناریوها به‌ترتیب اجرا شوند؛ هم‌زمانی فقط در case مربوط و پیش‌فرض حداکثر دو درخواست تولید هم‌زمان. تست محدودیت نرخ فقط با حد مشخص در محیط تست.
- «زود» یعنی قبل از یک شرط قابل‌مشاهده مانند ثبت conversationId یا آماده‌شدن منبع؛ «دیر» یعنی بعد از آن. صرف sleep نتیجهٔ وضعیت را اثبات نمی‌کند.
- برای سناریوهای حساس، فاصله‌های 0، 100، 300، 1000، 3000 و 10000 میلی‌ثانیه را به‌عنوان variant ثبت کن؛ زمان واقعی و state واقعی در لحظهٔ trigger هم ثبت شوند.
- در تست مرز وضعیت، یک‌بار درخواست را درست قبل و یک‌بار درست بعد از transition واقعی trigger کن؛ barrier/event کنترل‌شده به‌کار ببر.
- کندکردن انتقال bytes، کندکردن response مرورگر و کندکردن پردازش backend سه حالت متفاوت‌اند؛ بدون امکان کنترل پردازش، مدعی تست آن نباش.
- از polling/event معتبر و deadline استفاده کن. deadline از قرارداد/پیکربندی باشد؛ اگر نامعلوم بود مقدار آزمایشی را صریح برچسب بزن. تمام‌شدن deadline کلاینت، شکست قطعی یا تمام‌شدن عملیات سرور را اثبات نمی‌کند.
- caseهای race و شکست متناوب حداقل ۱۰ بار با fixture مستقل اجرا شوند؛ خط پایهٔ سالم قبل و بعد از سری تکرار شود.
- حداقل یک سری fixed-seed reproducible داشته باش. تعداد موفقیت/شکست را x/n همراه زمان‌ها و وضعیت‌ها گزارش کن؛ یک تکرار سالم رفع مشکل را اثبات نمی‌کند.
- اول متغیرها را یکی‌یکی تغییر بده؛ سپس تعامل‌های دوتایی و ترکیب‌های بحرانی را اجرا کن. ادعای پوشش همهٔ ترتیب‌های بی‌نهایت نکن.
- اگر به 429 یا محدودیت حساب رسیدی، برای دورزدن آن حساب/توکن عوض نکن؛ backoff مجاز و اثر محدودیت بر تست را ثبت کن.

## ۶. اجرای همهٔ پرامپت‌ها و اکشن‌ها

از config، UI و کد موجود، action-catalog.json بساز: actionId، عنوان، متن template، وابستگی به فایل/نقش، endpoint واقعی و شرط فعال‌شدن.
خلاصه، توضیح ساده، نکته‌ها، مقایسه، تمرین و برنامهٔ مطالعه فقط نام‌های قبلی‌اند؛ آنچه امروز در برنامه وجود دارد مرجع است.

این corpus آزمایشی را ثبت و در صورت نیاز برای fixture واقعی تطبیق بده:

| ID | پرامپت |
|---|---|
| P01 | سلام؛ بدون استفاده از فایل، تفاوت یادگیری و حفظ‌کردن را کوتاه توضیح بده. |
| P02 | مفهوم کسر را با یک مثال ساده توضیح بده. |
| P03 | فقط بر اساس منابع انتخاب‌شده، سه نکتهٔ اصلی را با ارجاع بنویس. |
| P04 | جمله‌ای که شامل عبارت یکتای fixture است را پیدا کن و مقدار عددی کنار آن را بگو. |
| P05 | دو منبع انتخاب‌شده را مقایسه کن؛ موارد اختلاف را روشن بگو. |
| P06 | از متن انتخاب‌شده چند پرسش تمرینی بساز؛ جواب‌ها را جدا بیاور. |
| P07 | برای مطالعهٔ همین موضوع یک برنامهٔ کوتاه پیشنهاد بده. |
| P08 | این سؤال به فایل ضمیمه‌نشده اشاره می‌کند؛ قبل از ادعای خواندن آن، وضعیت دسترسی را توضیح بده. |
| P09 | متن فارسی چندپاراگرافی همراه عدد، عبارت لاتین، newline و سؤال تکمیلی. |
| P10 | سؤال دوم یک گفتگوی قبلی: مثال پاسخ قبلی را ساده‌تر کن و فرض‌های آن را توضیح بده. |

- fixtureها با marker و اعداد ساختگیِ معلوم تهیه شوند؛ سؤال منبع‌محور پاسخ قابل‌بررسی داشته باشد.
- ابتدا P01 را با زمان‌بندی‌های مختلف اجرا کن تا متن عامل مخدوش‌کننده نباشد.
- **هر اکشن واقعی** را در حالت‌های بدون فایل، فایل در حال انتقال، فایل در حال پردازش، یک منبع آماده، چند منبع با آمادگی متفاوت و اجرای مجدد پس از اتمام آزمایش کن.
- برای هر اکشن ترکیب «اکشن→فایل→Send» و «فایل→اکشن→Send» و تغییر اکشن پیش از Send پوشش داده شود.
- موارد وابسته به فایل/نقش را طبق قرارداد بررسی کن؛ وابستگی واقعی را با باگ اشتباه نکن.
- کارت پرامپت طبق تصمیم محصول فقط متن قابل‌ویرایش را وارد composer می‌کند و خودکار ارسال نمی‌کند؛ اگر پیاده‌سازی زودتر درخواست/رزرو می‌سازد، همان رفتار ثبت و با تصمیم محصول مقایسه شود.
- زیرمجموعهٔ بحرانی را در دسکتاپ، تبلت و گوشی اجرا کن؛ تفاوت handler و keyboard/touch را هم ثبت کن.
- پاسخ متنی را با معیارهای محتوایی بررسی کن، نه تطبیق لفظی کامل؛ وضعیت HTTP، صحت پاسخ و صحت ارجاع سه بررسی مستقل‌اند.

## ۷. سناریوهای پایهٔ اجباری

برای هر سطر زیر یک case داشته باش؛ variants و repetitions با شناسهٔ فرعی ثبت شوند. حذف یا ترکیب سطرها بدون traceability مجاز نیست.
در صورت نبود قابلیت/fixture، دلیل BLOCKED یا NOT_APPLICABLE را با شاهد بنویس. نبود مشاهدهٔ خطا به‌معنی NOT_APPLICABLE نیست.

### ورود، نشست و آماده‌شدن صفحه

| ID | سناریو | اقدام | معیار بررسی |
|---|---|---|---|

## ۸. پوشش همهٔ خانواده‌های خطا؛ نه صرفاً 409

برای هر endpoint واقعی، ledger کدهای مستند، مشاهده‌شده و تست‌شده بساز:

- 4xx: اعتبارسنجی، احراز هویت، دسترسی، نبود/حذف منبع، تعارض وضعیت، پیش‌شرط، اندازه/نوع ورودی، محدودیت نرخ و هر کد دیگرِ واقعاً مستند/مشاهده‌شده.
- 5xx: خطای داخلی، dependency، upstream/gateway، عدم دسترسی موقت، timeout، ظرفیت و کدهای واقعی زیرساخت.
- کدهای کمتر رایج مثل 402، 423، 424، 425، 451، 505، 507 و کدهای اختصاصی vendor فقط در صورت ارتباط با قرارداد/محیط بررسی شوند؛ معنای آن‌ها را حدس نزن.
- 425 را صرفاً به‌معنی «کاربر خیلی زود کلیک کرده» فرض نکن. 408 سرور با timeout سمت کلاینت یکی نیست. هر قفل اپلیکیشن نیز الزاماً 423 نیست.
- یک error mapper عمومی که همه چیز را 409 یا 500 نشان می‌دهد شناسایی کن؛ status اصلی، status ترجمه‌شده و پیام UI هر سه ثبت شوند.
- تمام کدهای 400 تا 599 را در سطح logger/دسته‌بندی قابل ثبت نگه دار؛ لازم نیست برای کد ثبت‌نشده یا نامرتبط سناریوی مصنوعیِ واقعی‌نما بسازی.
- برای 5xxهایی که در محیط واقعی قابل‌تولیدِ کنترل‌شده نیستند، تست handling با UI mock یا integration ایزوله جدا انجام شود؛ خطای واقعی سرور NOT_RUN باقی بماند.
- پاسخ غیراستاندارد/غیرJSON proxy، خطای CDN، قطع stream، 3xx غیرمنتظره و شکست با 2xx نیز حذف نشوند.

**با تبدیل خطای واقعی به mock، ثابت‌کردن خروجی موفق، حذف assertion، catch عمومی یا اضافه‌کردن sleep بزرگ، تست را سبز نکن.**

## ۹. تحلیل علت و نسبت‌دادن مسئولیت

بعد از بازتولید هر مشکل، یک اجرای سالم و یک اجرای شکست‌خورده با حداقل تفاوت تهیه کن. timelineها را کنار هم بگذار و اولین نقطهٔ واگرایی را نشان بده.

برای 409 به‌ویژه بررسی کن:

- منبع واقعاً آماده بوده یا فقط upload تمام شده؟
- conversationId و source/version متعلق به همین گفتگو و حساب‌اند؟
- idempotency key برای retry همان intent ثابت مانده و برای intent تازه طبق قرارداد تغییر کرده؟
- همان operationId در دو handler، دو تب یا دو اکشن متفاوت ناخواسته استفاده شده؟
- عملیات قبلی in progress، completed، failed، canceled یا outcome unknown بوده؟
- رزرو/preflight منقضی، مصرف‌شده یا متعلق به payer/context قبلی است؟
- پاسخ دیرهنگام state مربوط به intent تازه را خراب کرده؟
- 409 از API اصلی آمده، از dependency ترجمه شده یا فقط در UI ساخته شده؟
- مشکل ناشی از payload خلاف قراردادِ کلاینت است، race در backend است، ابهام قرارداد است یا هنوز قابل‌تشخیص نیست؟

این پرسش‌ها فرضیه‌اند. بدون log/code شاهد، unique constraint، deadlock، خرابی provider، دوباره‌برداشت هزینه یا race دیتابیس را علت قطعی ننام.

طبقه‌بندی confidence:

- CONFIRMED: شاهد مستقیم کد/لاگ/trace معتبر یا نتیجهٔ کنترل‌شده‌ای که علت دقیق را اثبات می‌کند.
- SUPPORTED: الگوی بازتولید و مقایسهٔ کنترل‌شده با فرضیه سازگار است، ولی علت داخلی اثبات نشده.
- UNKNOWN: اطلاعات کافی نداریم؛ دقیقاً لاگ/شناسه/دادهٔ لازم را بنویس.

مالک پیشنهادی یکی از frontend / backend / AI service / infrastructure / contract / unknown باشد؛ اگر چند جزء دخیل‌اند سهم هر کدام را جدا توضیح بده.

## ۱۰. گزارش هر خطا؛ قابل‌ارسال به بک‌اند

برای هر issue، این قالب را کامل کن:

- issueId و عنوان روشن.
- شدت و اثر واقعی بر کاربر؛ نه شدت براساس شمارهٔ HTTP به‌تنهایی.
- محیط، build، نقش تست، زمان و endpoint/method.
- caseId، prompt/action، ترتیب عملیات و تأخیر واقعی هر مرحله.
- fixture و وضعیت منبع/گفتگو/عملیات پیش از خطا.
- request payload پاک‌سازی‌شده و headerهای مرتبط.
- HTTP status واقعی؛ businessCode، متن خطا و response body پاک‌سازی‌شده.
- تمام درخواست‌های وابسته و retryها؛ trace/request/operation ID در صورت وجود.
- انتظار و منشأ انتظار: LIVE_CONTRACT / PRODUCT_DECISION / OBSERVATION / PROPOSAL.
- نتیجهٔ واقعی در UI، API و history.
- نرخ بازتولید x/n با retryها به‌عنوان attempts مستقل؛ شکست اولیه حفظ شود.
- شاهد HAR/trace/screenshot/log و مسیر دقیق آن.
- علت، سطح اطمینان، شواهد موافق و شواهد لازمِ غایب.
- مالک پیشنهادی و دلیل آن.
- پیشنهاد مشخص برای بک‌اند و در صورت لزوم فرانت‌اند/AI؛ پیشنهاد را واقعیت فعلی جا نزن.
- تست پذیرش اصلاح: قدم‌ها و نتیجه‌ای که مانع بازگشت همین مشکل می‌شود.
- replay حداقلی با fixture و credential در environment، بدون نوشتن token واقعی داخل فایل. side effectهای replay را روشن کن.
- در نبود دسترسی به لاگ سرور، سؤال دقیق برای تیم بک‌اند و شناسه/بازهٔ زمانی لازم.

پیشنهاد «کمی تأخیر بگذارید» یا «retry کنید» به‌تنهایی کافی نیست. با شاهد مشخص کن کدام state transition، پیش‌شرط، کلید، قرارداد خطا یا recovery باید تغییر کند.
برای 500 نیز فقط «مشکل سرور» ننویس؛ مرحله و trace و dependency قابل‌مشاهده را دقیق مشخص کن.

## ۱۱. فایل‌های خروجی اجباری

خروجی‌ها در یک پوشهٔ مشخص reports/api-error-audit/<runId>/ ذخیره شوند:

4. action-catalog.json و api-contract-map.json: فهرست اکشن‌ها و endpointها و منبع انتظارات.

6. attempts.jsonl: هر تلاش و هر درخواست وابسته با status واقعی؛ retryها سطر مستقل و attempt مستقل داشته باشند.

9. evidence/: HAR/trace/log/screenshot و payloadهای پاک‌سازی‌شده؛ endpoint اصلی و وابسته‌ها قابل‌ردگیری باشند.
10. repro/: تست/اسکریپت حداقلی قابل‌اجرا و دستور اجرا با متغیرهای محیطی و fixture. اگر ابزارهای فعلی کافی‌اند همان‌ها را توسعه بده.

### شکل جدول خلاصهٔ نهایی

| سناریو/variant | اکشن | مرحلهٔ خطا | HTTP | کد تجاری/شبکه | انتظار | نتیجه | علت و اطمینان | مالک | شاهد |
|---|---|---|---|---|---|---|---|---|---|

آمار را جدا گزارش کن: تعداد caseهای برنامه‌ریزی‌شده، variants، اجراشده، PASS، FAIL، BLOCKED، NOT_RUN، NOT_APPLICABLE، تعداد request/attempt و تفکیک 4xx/5xx/transport/business/parse/stream.
تعداد تست‌های شبیه‌سازی را با تعداد درخواست‌های واقعی سرور جمع نزن و آن را درصد سلامت سرور معرفی نکن.
خطاهای موردانتظار تست منفی در آمار HTTP می‌آیند ولی الزاماً issue نیستند.

## ۱۲. شرط پایان

- هر ۱۰۷ سناریوی پایه و هر اکشن کشف‌شده حسابرسی شده باشد: اجرا یا علت روشنِ اجرا نشدن.
- ترکیب‌های بحرانی زمان‌بندی، ترتیب معکوس فایل/اکشن، صفر منبع، تکرار، پایان‌نامعلوم و بازیابی پوشش داشته باشند.
- همهٔ خطاهای مشاهده‌شده، حتی 4xx/5xx خارج Swagger یا 200 دارای خطا، ثبت و دسته‌بندی شده باشند.
- برای هر issue قابل‌بازتولید، شاهد و تست پذیرش موجود باشد.
- برای سناریوهای race، نرخ بازتولید و trace حداقل ۱۰ تکرار موجود باشد؛ استثنا و علت محدودیت صریح ثبت شود.
- علت قطعی و فرضیه و نبود شاهد از هم جدا باشند.
- در صورت نبود credential، محیط، fault harness یا لاگ، BLOCKED گزارش بده و بقیهٔ کارهای مستقل را ادامه بده.
- همهٔ موارد اجراشده را پشت یک ادعای «تست شد» پنهان نکن. اگر فقط بخشی اجرا شد، همان بخش و کار باقی‌مانده را بنویس.
- هیچ ادعای اصلاح، استقرار، تست واقعی بک‌اند یا پاک‌سازی داده بدون اجرای واقعی و شاهد نکن.

## ۱۳. مرجع معنای کد HTTP

معنای کدهای استاندارد را با منابع اولیه بررسی کن؛ معنای کد تجاریِ ماکان از قرارداد/کد/لاگ خود پروژه استخراج شود:

- RFC 9110، بخش 15: https://www.rfc-editor.org/rfc/rfc9110.html#section-15
- HTTP Status Code Registry: https://www.iana.org/assignments/http-status-codes

تمرکز نهایی: «کدام ترتیب و کدام state باعث چه درخواست و چه پاسخ می‌شود؛ علت چقدر اثبات شده و دقیقاً چه تغییری به کدام تیم پیشنهاد می‌شود».
